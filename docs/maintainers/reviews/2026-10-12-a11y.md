# Accessibility review, 2026-10-12 (HANDOFF P0-5)

Maintainer document; not shipped to job seekers.

## Scope and method

- **Target:** WCAG 2.2 level AA. WCAG 3.0 is still a Working Draft, so it is not a target; where its draft outcomes (plain language, clear words, help available, no time pressure) point the same way, that is noted as "3.0 readiness".
- **Surfaces:**
  1. The 7 Claude Code panels (mods): `outbox`, `pipeline` (pane and band), `contacts-board` (pane and band), `job-inbox` (pane and band), `apply-kit`, `interview-room`, `due-alerts` (start-of-session pop-up), in `.claude/skills/<mod>/hooks/`.
  2. The conversation: `AGENTS.md`, `CLAUDE.md`, the skills in `.claude/skills/*/SKILL.md`, and the chat versions of the panels in `.agents/skills/`, read as text.
  3. Pages and PDFs: reviewed separately by the pages agent (section at the end).
- **Method, panels:** read every `register.tsx|ts` and the mod API's own type file for Claude Code 2.1.296 (21,461 lines, written by the `plugin-authoring` skill) to see what the host offers. Then fixed what was confirmed and added tests. Commands: `claude plugin validate --strict` and `claude plugin test` on each panel (`bash scripts/ci/check-mods.sh`), plus `bash scripts/ci/check-parity.sh`. The five `csvdate.ts` copies were not touched and are still byte-identical (one md5 for all five).
- **Method, conversation:** a read-only text review of the skills against the checks listed in P0-5. Every finding quotes a line. Six of the quotes were re-checked by hand: interview-prep:14, mock-interview:26, :45 and :51, start:14, today:19 and :26. The ⓘ quote at start:116 was also confirmed.
- **What was not done:** no screen reader (VoiceOver, NVDA) and no real terminal theme was used. Everything that depends on how the host draws or speaks is marked **needs a human test**. The test host has no focus ring: `$.ui.focus` fails there with `HooksError: no implementation for ui.focus`, seen in a scratch probe. So the new focus moves are written to the API's documented contract, are best-effort (errors swallowed), and need a human test.

### What the host offers (from the API types, verified by grep)

- **Accessible names:** a `Button`'s `label` is its name. Children, when given, are drawn in its place ("The label then names the control"). On a desktop, `role="dismiss"` draws the native close control, and the label is its accessible name. `Image` has a required `alt` that is "read by a screen reader".
- **Focus:** `autoFocus` (only when the site takes the keyboard), `$.ui.focus({ requestId, key })`, and a `ui.focus` event. Escape "never arrives: it returns the focus" to the prompt. A user enters a pane or the band with **Ctrl+X then Tab**, a click, or `open({ focus })`. Tab and the arrow keys move the ring. The engine inverts the focused button.
- **Color:** `ThemeKey` names (`text`, `warning`, `error`, `success`, `suggestion`, …) follow the user's terminal theme. The panels use only theme keys and `dimColor` (grep: no raw color, no background color).
- **Announcements:** none. The types have no live-region or announce API. "screen reader" appears only twice, for `Image.alt` and for the prompt hint line. Status lines in panels are plain text, and toasts are transient.
- **Hotkeys:** `hotkey` (one key, only while the site holds focus). No panel uses one.

**Screen readers in terminals (honest limit):** a screen reader reads a terminal UI the way the terminal exposes it. VoiceOver with Terminal.app, NVDA with Windows Terminal, and VS Code's terminal accessibility mode each behave differently. Redrawn regions may be re-read or skipped. The panels can't control this. Every panel has a chat route that gives the same flow as plain text ("show my board", the mock-interview chat version), and the mock-interview skill tells screen-reader users to turn off the room's read-aloud or use chat.

## Needs a human test (checklist for a release candidate)

1. VoiceOver plus Terminal.app, and NVDA plus Windows Terminal: open each panel with its slash command. Tab through it, press a confirm row and Cancel, and listen for the per-card names and whether the notice line is read.
2. The Claude desktop Code tab with VoiceOver: native button names ("Copy (Email)"), the dismiss control, and the focus after a card leaves.
3. Light, dark and high-contrast terminal themes: readability of dim text, `warning` (yellow on light themes) and `suggestion`.
4. An 80-column terminal: unasked panes wait, `/outbox` opens, and labels don't wrap.
5. The Interview Room with a screen reader: read-aloud off, clock off, then answer by dictation and by typing.

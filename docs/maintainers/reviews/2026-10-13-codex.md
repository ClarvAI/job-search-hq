## Summary

67 raw findings, 14 duplicates, **53 unique**: 39 CONFIRMED, 13 PARTLY, 1 REJECTED.
Severity of the 52 confirmed or partly confirmed: **7 high, 14 medium, 31 low**.

- **All seven highs are ways around the public-repository check**, and every one returned **allow** in the probe (sh and ps1 alike, except J5-08, where only ps1 allows). Three of them are gaps left by the 2026-10-12 fixes: the fallback `|| urls="$remote"` (the old fix suggestion "deny if resolution fails" was not done), the attached `-c<key>=<value>` form, and file-based GraphQL bodies. SECURITY.md:38 still says the check "follows git aliases, `-c` settings, URL rewrites and SSH host aliases". The opt-in pre-push hook would catch most of them (it checks the real destination git hands it), which is the best argument for offering it more firmly.
- **Codex specifically:** the Codex shell tools' `workdir` is ignored by the guard (J1-01), and on Windows `guard.ps1` can't see inside `powershell -Command "..."` or `bash -c '...'` and ignores `$env:GIT_CONFIG_*` (J5-07, J5-08), so the Windows Codex user, whose only protection is `guard.ps1`, is the most exposed. The Codex wrappers, rules and hook wrappers are otherwise wired correctly; nothing found stops a Codex workflow outright.
- **Routines (new):** three medium logic gaps: a paused search never pauses routines (J4-11), a closed search silences benefits-certification reminders the offer flow says must keep running (J4-09), and a failed or skipped inbox run moves the inbox window forward (J4-10). Plus the follow-up routine never drafts the playbook's second post-interview check (J2-03). No way was found for an email or posting to make a scheduled run send, publish or submit: those stay blocked by the guard and the written rules.
- **Over-restriction:** the guard's false positives are real but narrow (a surname in a job URL, an Outlook calendar event, a word like `smtplib` in a search, `FromBase64String`). None blocks a core workflow; each has a cheap fix.

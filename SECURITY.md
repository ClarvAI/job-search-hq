# Security

## Reporting a problem

If you find a way to make the assistant send email, submit something, leak a user's personal data, or get around the safety checks described below, please report it privately:

- On GitHub, open this repository's **Security** tab and choose **Report a vulnerability** (private vulnerability reporting). Please don't open a public issue for it.
- Include the app and version (Claude Code or Codex, desktop or terminal), your operating system, the steps that reproduce it, and what happened.
- **Never include anyone's real personal data** (resumes, emails, contact lists). Use made-up examples.

We aim to reply within a week. This is a volunteer project, so there's no bug bounty.

Ordinary bugs go in a regular issue (see the bug report template).

## What protects the user

The main protection is the rules the assistant follows (`AGENTS.md`): it drafts and the user decides; it never sends email, submits applications, or posts anything unless the user turned on a mode that allows it and confirmed. Rules are followed by an AI model, so they can fail. Two technical layers sit underneath.

### 1. The guard (a hook that checks tool calls before they run)

`.claude/hooks/guard.sh` (and `guard.ps1` on Windows) runs before the assistant uses certain tools, in both apps. It blocks:

- **Email:** anything except reading, searching, and creating or updating drafts (no send, reply, forward, delete, label or archive). Any other connected app whose action sends, replies, forwards, posts, shares, publishes, invites, submits, trashes or deletes is blocked too (the verb is read from the whole tool name, kebab-case and camelCase included), and so is adding, changing or removing collaborators, guests, members or permissions (Zoom's file collaborators, for example). Automation services (IFTTT, Zapier, n8n, Pipedream), contacts apps (such as Contacts+), any tool that pushes, syncs, exports or uploads contacts or people, and feedback sent to an app's maker: anything but read makes Claude ask the user and Codex block.
- **Calendar and meeting tools** (Google Calendar, Outlook, Calendly, Zoom and similar): anything except reading and adding an event or meeting with no attendees, guests, invitees, registrants or alternative hosts to the user's own calendar or account. Changing, cancelling, deleting or controlling a meeting is blocked.
- **Browser and computer use:** sending an automated browser to Gmail, Outlook or LinkedIn, including through link shorteners and through browser tools that run code on a page (`location=` and similar count as navigation). Look-alike addresses are folded the way a browser does first (full-width letters and dots, and invisible characters such as a soft hyphen or zero-width space are removed). It sees addresses the assistant asks for; it can't see which site a tab the user already opened is showing.
- **Web fetches:** addresses that look like they carry personal data (an email address, the user's phone number, their surname in the query or their full name anywhere in the address, or a large block of data). A surname alone in the site name or path (a "baker" job) doesn't count. This is a pattern check and can't catch every disguise.
- **Shell:** pushing this folder to a public GitHub repository, creating a public repository or gist, writing to a public repository with `gh api` or `gh release` (a `gh api -X GET` read is fine), a `gh api graphql` request whose query comes from a file, standard input or a variable, or making a repository public; a push in the same command as a remote, alias or config change (including `-c`, `--config-env`, `GIT_CONFIG_*` and PowerShell's `$env:GIT_*`); a push from a folder that doesn't exist. Variables in `cd`, `-C` and `GIT_DIR` are expanded first, Codex's `workdir` is followed, and a script passed to `bash -c`, `sh -c`, `pwsh`/`powershell -Command` or `cmd /c` is checked like any other command. Also sending mail from the computer (AppleScript to Mail or Outlook, Outlook COM, `Send-MailMessage`, SMTP libraries, `sendmail`, `git send-email`; the word alone in a search or a commit message doesn't count) and opening Gmail, Outlook or LinkedIn with `open`, `start` or a browser module. `.githooks/pre-push` repeats the push check inside git when turned on; `.githooks/commit-msg` removes AI attribution lines from commit messages.

If the guard script crashes or is missing, the hook command turns that into a block. In Codex the guard reports a block on stderr with exit code 2, so text a login profile prints can't hide it, and the Unix hook commands run under `/bin/sh` whatever the user's shell is.

What it does **not** cover:

- **Time-outs.** The limit is 30 seconds in both apps. Claude Code 2.1.295 and later block the action when the guard times out (`onFailure: block`); older Claude Code versions and Codex cancel the guard and let the action go ahead. In practice the guard finishes in milliseconds; only the `git push` check makes a web request (to ask GitHub whether the repository is public), and it stops at the first repository it can't confirm.
- **Codex:** hooks run only after the user reviews and trusts them, and again after any change to them; until then the guard does not run. Codex hosted tools such as its web search don't go through hooks at all, and OpenAI notes that some specialized tool paths can skip hooks ("a useful guardrail, not a complete enforcement boundary"). File edits (apply_patch) are not checked by the guard.
- **Claude Code:** the guard checks shell commands, web fetches, and connector/MCP tools (Gmail, Calendar, the built-in browser, Claude in Chrome, computer use). It also checks commands run through Claude Code's separate PowerShell tool on Windows. File edits and web searches are not checked by the guard. Project hooks run only after the user trusts the folder, and only when Claude Code is started in the top folder. On Windows the hook commands need Git for Windows (Git Bash); without it Claude Code runs hooks in PowerShell, the guard command can't run there, and the tool call goes ahead: the permission deny rules below are then the only technical block, so Git for Windows is a requirement.
- **Other apps.** In a regular Claude chat with a folder (Cowork), Claude Code on the web, Codex cloud, and other assistants that read `AGENTS.md` (Cursor, GitHub Copilot, Gemini CLI, Devin, OpenCode, Amp, Factory), treat the guard as not running. Some of those apps can load `.claude/settings.json` hooks, but they let the action through when a hook fails, and none was tested with this guard. The written rules are the only protection there. `docs/platforms.md` has the app-by-app details.
- It reads tool requests, not the screen. It can't stop the user from doing something themselves, and it can't stop a program the assistant runs from doing something the command line doesn't show.
- **The public-repository check reads the command line.** It follows git aliases (every push in a shell alias), URL rewrites saved in git's settings (`insteadOf` / `pushInsteadOf`), SSH host aliases for GitHub (a trailing dot included), Codex's `workdir`, and scripts passed to `bash -c`, `sh -c`, PowerShell's `-Command` or `cmd /c`. A cd inside brackets or `bash -c` doesn't last, so a later push is checked from every folder the command was in. It blocks rather than follows a push in the same command as a settings change (`-c`, `--config-env`, `GIT_CONFIG_*`, `$env:GIT_*`), a push from a folder it can't find, and commands that hide what they run (base64 or similar fed to a shell, a program name in a variable or built in brackets). It can't see inside a script saved in a file and run later, and it doesn't follow every way of changing folder (`env -C`, a shell function). The optional `.githooks/pre-push` hook runs inside git and sees the real destination, so it covers that case; it is off until the user turns it on (`git config core.hooksPath .githooks`, offered by `/start` and `/health`, never enabled without their yes). Neither check knows hosts other than GitHub (GitLab, Bitbucket, self-hosted git, cloud drives): pushes there aren't checked at all. If GitHub can't be reached within a few seconds to confirm a repository is private, the push is blocked.
- **Browser destinations are matched by address.** Addresses are decoded first, so a search engine's `url?q=` link to a blocked site is caught, and well-known link shorteners are blocked; but a site that redirects on its own server to Gmail, Outlook or LinkedIn can't be seen in advance. What the assistant types into a page on any other site isn't checked: keeping coach mode read-only on employer sites is a rule, not a block.
- **Web-fetch checks are patterns,** not a guarantee: data split across a URL or encoded in an unusual way can get through.

### 2. App permissions (Claude Code)

`.claude/settings.json` asks before edits to the product's own instructions and settings (`AGENTS.md`, `CLAUDE.md`, `.agents/`, `.codex/`, `.githooks/`, `VERSION`, `product-manifest.json`; Claude Code already protects `.claude/`), before edits to the user's master resume and preferences, and before shell commands that name a path in `profile/` and could change it (redirects such as `>`, `cp`, `mv`, `rm`, `tee`, `sed`, `awk`, `perl`, `python`, `node`, `ruby`, `touch`, `ln`, `rsync`, `tar`, `unzip` and similar, and the PowerShell equivalents such as `Set-Content`, `Copy-Item`, `Move-Item`, `Remove-Item` and `>`). It blocks `curl`, `wget`, `git push` and `rm -rf`, and denies the Gmail, Superhuman and Google Calendar connector tools that send, reply, forward, trash, respond to or change things, so those stay blocked for the assistant even if the guard can't run (the Outbox panel's own Send, after the user's confirmation, is the panel's call, not the assistant's). Sessions start in Claude Code's auto mode (the project no longer sets a starting mode): a separate classifier reviews actions instead of routine prompts, while the ask and deny rules here still apply. These rules match the command text the assistant writes: a command that reaches `profile/` without naming it (a script file, a variable, a `cd` first) isn't caught, and the Claude Code documentation is clear that they are not a security boundary around a program. Two further checks don't depend on them: the Outbox panel sends only after the user has confirmed send mode once inside the panel, and assisted mode is confirmed by the user in chat before the first form each session (a rule the assistant follows).

Codex uses its own approval and sandbox settings, which the user controls in Codex.

## Data handling

The project has no server and no telemetry. Data stays in the user's folder, except what goes to the AI provider, the copies the AI app keeps in its own folder (chat history, memories), web searches and fetches, and any connectors, voice input or publishing the user turns on. `docs/privacy.md` maps every path, app by app; `DISCLAIMER.md` has the short version. User data files are kept out of git (`.gitignore`), and backups are made with `/my-data` as zip files the user keeps. Codex is set not to make memories from chats in this folder (`.codex/config.toml`).
